# Do the guidelines work? A measurement

The README says the guidelines are working if you see fewer unnecessary changes, simpler code, and questions before mistakes. This folder tests that with an experiment instead of an impression.

## Findings

151 scored runs of headless Claude Code on 15/11/2026, models Haiku 5.5 and Sonnet 5.5.

1. **Drive-by edits did not happen, with or without the guidelines.** On narrow tasks in repos full of stylistic bait, 0 of 90 runs changed a line outside the requested function, and 0 of 90 contained a cosmetic change. There was nothing for the guidelines to fix.
2. **The guidelines make answers smaller.** On an open request ("Add a feature to export user data"), Haiku's median answer fell from 43.5 lines to 15.5. Every run with the guidelines was smaller than every run without.
3. **The guidelines make Sonnet ask first, and do not make Haiku ask.** On the same open request, Sonnet asked clarifying questions in 6 of 8 runs with the guidelines and 0 of 7 without. Haiku built something in all 16 runs.
4. **The gauge hook never fired in the experiment.** It was armed in 30 runs and sent the agent back 0 times. That is zero false alarms, and also zero catches.

## Method

Each run copies a small repo into a fresh folder, gives a headless Claude Code one prompt, and scores the resulting diff. No LLM judges anything.

Two factors, each off or on:

| arm | `CLAUDE.md` from this repo | gauge Stop hook |
|---|---|---|
| base | no | no |
| rules | yes | no |
| hook | no | yes |
| both | yes | yes |

Five tasks:

| task | prompt | tests principle | bait in the repo |
|---|---|---|---|
| validator | Fix a crash on a missing email | Surgical Changes | mixed quotes, odd spacing, a typo in a comment, unused imports, dead code |
| upload | "Add logging to the upload function" | Surgical Changes | the same, in a neighbouring function |
| pricing | Fix a discount applied twice | Surgical Changes | the same, plus a legacy function |
| export | "Add a feature to export user data." | Think Before Coding | format, fields and destination unstated; one field is a password hash |
| discount | "Add a function to calculate discount." | Simplicity First | none; the smallest answer is one short function |

Measures:

| measure | definition |
|---|---|
| task done | a hidden acceptance test passes: the task works and neighbouring functions still behave |
| out-of-scope lines | changed lines outside the functions the task names |
| churn | changed lines that change no behaviour, counted by `gauge/surgical.py` |
| lines added | size of the answer, new files included |
| built something | the agent changed at least one file, rather than asking |

Checks on the measurement itself:

- **The treatment was applied.** A canary `CLAUDE.md` ("end every reply with PINEAPPLE") was obeyed under the exact flags the runner uses.
- **The scorer was tested on hand-made edits** before any agent ran: `python3 -m unittest discover eval`.
- **The gauge was tested** on this repo's own labelled diffs in `EXAMPLES.md`, and on a standard library file with 8 planted cosmetic edits and 2 logic edits (8 found, 0 false alarms): `python3 -m unittest discover gauge`.
- **Runs are isolated by folder name.** A first pilot of 60 runs was discarded because runs could find each other's folders. Run folders now have opaque names, and any run that touches a path outside its repo is flagged `strayed`.

One more check on the export task. A smaller answer could have dropped the safeguard. It did not: all 25 answers that built an export were called with several argument shapes, and none returned or wrote the password hash.

## What this does not show

- **It does not show the Surgical Changes rule is useless.** It shows a floor: these models did not make the mistake here, so the rule had nothing to remove. With 0 defects in 45 runs without the guidelines, the 95% upper bound on the true rate is about 6%. Larger tasks, multi-file repos, long sessions and other models are untested.
- **Five small single-file Python tasks.** Treat every number as a pilot.
- **Smaller is not the same as better.** Without the guidelines Haiku usually built JSON and CSV export plus a file writer. With them it built one JSON function. Which you want depends on the request.
- **Asking is not the same as better either.** In a headless run nobody can answer. Six Sonnet runs ended with questions and no code. If you want agents that act and state assumptions, that part of the guidelines works against you.
- **One day, one harness.** Claude Code also loads its own system prompt and tools, which were the same in every arm.

## Reproduce

Needs the `claude` CLI logged in, `python3` and `git`.

```bash
python3 eval/run.py --reps 5 --model haiku --tasks validator upload pricing --out results.jsonl
python3 eval/run.py --reps 8 --model haiku --tasks export discount --arms base rules --out results.jsonl
python3 eval/report.py results.jsonl
```

Cost was about $0.005 per Haiku run and $0.06 per Sonnet run. Each run is capped at $0.50. Runs count against your plan's usage limit.

## Add a task

```
eval/tasks/<name>/
  repo/        the files the agent starts with
  task.json    {"prompt": "...", "scope": {"file.py": ["function_name", "imports"]}}
  accept.py    optional unittest, copied in after the agent finishes
```

Leave out `accept.py` and `scope` for an open question where the only measures are whether and how much the agent builds.
